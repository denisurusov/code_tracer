The operating model · 1 of 2

Code leaves under governance. Nothing governs code coming in.

Contributing to open source is already a controlled path — one inspected route, policy enforced, nothing leaving unexamined. Code arriving from outside has no equivalent. It comes with claims about itself, and nothing checks them.

Two directions, one control solid = governed · dashed = the gap
The bank
Outbound · GitProxy
Contributions pushed to FINOS through one inspected, policy-enforced path.
FINOS · open source
The bank
Inbound · nothing equivalent
Hardened releases and FINOS-native projects arrive with claims about themselves, and no mechanism that checks them.
FINOS · open source
Hence An evidence-based trusted pipe: an on-prem gate that admits or refuses inbound code mechanically, and a ledger of what we then rely on.

The two are not mirror images, and the design does not treat them as such.

The operating model · 2 of 2

Three state machines across two zones

Three different things move at three different speeds, and conflating them is the mistake the model exists to avoid. A product is the library. A project is one scope of work on it. A package is what that project ships. Each has its own states, and each is identified differently.

What to look at
5Outcome first, evidence second. The one thing an operator must be able to state out loud sits at the top in plain words.
6Required beside delivered, on every row. The contract's terms are worthless on screen unless the reader can see the threshold and the measurement side by side. "95%" alone says nothing; "95%, floor 90%" is a judgement.
7"Identical to 3.2.1" is not "everything passes". The wording matters — a newly-passing test is as much a behaviour change as a newly-failing one, and the column has to carry that.
8Timeliness is an acceptance criterion too. The delivery deadline sits in the same table as the technical thresholds, because a late fix is a failed fix.
9The trail is described, not named. "Proof the flaw fails on 3.2.1 and passes here" carries meaning; L5 does not. The level codes stay as a small reference column.
10Only L9 is ours. The ·in / ·out marker keeps the perimeter visible even inside the evidence list.
11"4 of 4 agreed, 3 required" states the threshold and the result together, so the reader never has to know what a quorum is.
12Headroom is separate from met. A criterion can pass and still be uncomfortable. Coverage cleared its floor by 5.2 of the available 10 points — amber — and that is invisible if the column only shows a tick.
13Four criteria are deliberately unscored. Where the requirement is pass-or-fail, the headroom cell is hatched rather than given an invented number.
14No clock on the bank. The timetable records when the decision was made but sets no target for it — the review takes as long as the evidence requires.
15One live control, and it is not a write. Re-running the check emits a new decision record. The future sign-off control is visibly disabled and dated.

Underneath

Nothing on these screens is a new format

Every record, identifier and signature above is an existing open standard — most of them already running somewhere in a bank. The gate is not new infrastructure to trust; it is tooling the bank already operates, pointed at a new policy. That is the single most important adoption argument in the design, so it gets a screen of its own.

The refusal case is not yet drawn. Every screen here shows a fix being accepted. A refused package naming the rule it failed is still to come, and until it exists this mockup shows only half of what the gate does. Some values are invented. The package, versions, contract, flaws, schedule, thresholds and quorum come from the fixture scenario; fingerprints, test counts, application names and the re-issue's details were made up to make the screens concrete.
