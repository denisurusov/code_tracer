**User:** I want to get back to the proposal that the outside part of the bundle (collection of meta-data file hashes and pointers) has to be assembled into a single file, stored in a central repo and hashed (git hash)

**Claude:** "**The shape is right.** Making the core a flat manifest — one file, listing a sha256 and a locator per element — beats an OCI image index for the job the core actually has: **It is the citable half, so it should be readable.** […] **It answers the core-availability open item.** The master repo is already the alliance's never-deleted, tagged, released publication surface (topology §3). The contract already lives there this way […]. **It matches the delivery manifest exactly.** That is already a list of digests frozen by a log entry. […] **Issuance becomes a reviewed merge.** […] **It is kilobytes.** […] **One correction, and it matters.** Identity should be `sha256` over the file, with the git blob SHA kept as a locator only. A git blob SHA is SHA-1 over `blob <len>\0` plus content. SHA-1 has had practical chosen-prefix collisions since 2019, and the cost has only fallen. Every other subject in this design is sha256-bound — chain principle #1, admission rule 12 — so keying the top-level evidence identifier on SHA-1 would put the weakest hash in the chain on the one value that gets handed to a regulator and compared between members. […] Konspekt's README is right that the blob SHA 'resolves and verifies structurally'; that standard is correct for a knowledge graph and too weak for an admission gate. So: `coreDigest = sha256(core file bytes)`. `git hash-object` stays useful for finding and fetching the file, and no admission rule keys on it — the same status the attestation index already has, a lookup and never evidence. **Second point […].** A file of digests and pointers is still a commitment to the contents. Every entry names bytes by sha256, so hashing the list is a Merkle root written out as a list — a wrong pointer fails immediately against the digest it claims to serve. That lets the core stay small while the bytes travel separately, resolved online by ③ before the envelope seals […]."

**Claude:** "**3 — suggested shape** `cores/{contractId}/v{N}/{seq}.json` […] Parallel to `contracts/{contractId}/v{N}.json` in the same master repo […]. The directory-per-contract-version exists because a core can legitimately be sealed more than once. `n` grows and quorum membership changes, so a fourth VSA can arrive after a core was sealed on three. Re-sealing gives `{seq}` = 2 with `supersedes: <prior coreDigest>` inside the file […]. No index file. 'Which core for this candidate?' resolves through the accepted contract, exactly as the `(package, line)` registry is a projection over accepted contracts […]. **Freeze: a Rekor entry over the core's sha256 at seal time** — the same instrument that already freezes the delivery manifest […]. It also means the claim survives a force-push, a repo migration, or the alliance losing the repository: path and git history are navigation, and the digest plus log entry is the freeze. […] **4 — JSON, with byte-stability specified.** Since the sha256 over the file *is* the identity, serialization has to be pinned or the digest breaks the first time anyone round-trips the object. Canonical form: RFC 8785 (JCS) — sorted keys, no insignificant whitespace, UTF-8 — with a trailing LF. […] Schema at `schemas/core/v{N}.json` in the master repo, with the schema version pinned inside the file […]."
