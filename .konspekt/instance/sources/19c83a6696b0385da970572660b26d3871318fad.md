**Claude:** "**#3 Bundle freshness.** Offline verification forfeits TUF's own freshness guarantee, so the gate needs a stated maximum age. I'd suggest **two separate clocks**: trust-root snapshot ≤ 7 days (it changes rarely, and staleness risk is a revoked key still looking valid), checkpoint set ≤ 24 hours (it changes constantly). Both configurable per-bank downward but not upward, and a stale bundle is a *reject with a named rule*, not a warning. **#4 Revocation semantics.** Record-an-exposure with a review trigger, not forced re-verification. Forcing re-verification means one revoked key can invalidate hundreds of admitted candidates simultaneously — a self-inflicted outage, and the artifacts themselves haven't changed. The ledger already answers 'which candidates rest on this signer'; the exposure surfaces in the console and the risk function decides. **#6 Quorum parameters.** Now that verification is a duty, `n` ≈ active membership. I'd propose **k = 3 with zero dissent** — matching the contract doc's existing `\"k\": 3` — with the caveat that k should be a *floor expressed as both* an absolute and a fraction (say ≥3 and ≥⅓ of active verifiers), so it doesn't silently weaken as membership grows."

**User:** Take all 3 as recommended
